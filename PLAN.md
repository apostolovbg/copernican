# Copernican Suite Development Plan
**Last Updated:** 2025-08-31

## Overview
Copernican Suite has grown from a single script into a modular, cross-platform
cosmology toolkit. The project now pursues a structured development cycle
where
new work happens on a dedicated branch and only mature code is merged into the
stable main branch. Tags mark stable states *after* each merge to main, but
tagging alone will **not** trigger automated packaging yet. The following plan
consolidates current goals, expectations and long-term directions based on our
recent discussions.

## Branching and Release Strategy
- Use a long-lived `work` branch for active development. Merge `work` into
  `main` only when the code is verified to be stable.
- Apply semantic versioning. Each tagged release corresponds to a stable
commit on `main` (e.g. `v3.6.12`, `v3.7.0`). Patch tags are created only
when a critical fix warrants a new public release.
- Tags are pushed manually after verifying the merged code. Packaging on tag
  is
  intentionally deferred; artifacts generated by CI remain for testing rather
  than immediate distribution.

## Continuous Integration
- GitHub Actions will act as the automated “assembly line”. Every push and
  pull
  request should spin up fresh machines for Windows, macOS and Debian-based
  Linux.
- Each job will install dependencies, run the unit-test suite and lint the
  code
  to maintain PEP8 and PEP257 compliance. Failures should stop the pipeline
and
  signal that the commit needs fixes before merging.
- After tests and linting, each job uses the platform's start script to verify
  the automatic virtual-environment workflow. Any logs are uploaded as
  artifacts for manual inspection.
- Pre-commit hooks (Black, Isort, Ruff or Flake8) will ensure consistent
  formatting before changes are committed. CI will run `pre-commit run --all-
  files` to guarantee uniform style across platforms.

## Packaging and Launchers
- Distribution relies on the `start.*` scripts which bootstrap a local `.venv`
  and install dependencies automatically.
- Users need only a system-wide Python 3.12+ installation.
- CI verifies the launchers on Windows, macOS and Linux.
- No standalone executables are planned.

## Version Management
- The runtime version is derived from package metadata using
  `importlib.metadata` through a helper that falls back to `"0+unknown"` when
  metadata is unavailable.
- `setuptools_scm` reads Git tags to embed accurate version numbers during
packaging. When a commit on `main` is tagged (e.g. `v3.6.12`), future
builds will report that version automatically.
- Version bumps follow semantic rules: increment **MAJOR** for breaking
  changes, **MINOR** for backward-compatible features and **PATCH** for fixes.
  Documentation-only commits may omit a version change.

## Testing and Quality Assurance
- `python -m unittest discover` remains the canonical way to run the test
  suite. Developers can also invoke `copernican.py --run-tests` to execute the
  same tests via the main entry point.
- Tests cover model interfaces, data loaders and regression checks for
  supported datasets. Future additions should extend coverage, especially as
  new engines, parsers or GUI components appear.
- CI must execute the full test suite on every push to prevent regressions.

## Compliance and Documentation
- Code and documentation should align with PEP8 (style) and PEP257
  (docstrings). Every public function, class and module needs clear
  explanations of both behaviour and rationale.
- README.md and AGENTS.md stay synchronized; any change to development laws or
  contributor expectations must appear in both files.
- The project’s license permits reuse and adaptation of individual modules
  while forbidding redistribution of the suite as a whole and banning patents
  on any included code. Derivative works must respect these restrictions.

## Future Directions
- Introduce a cross-platform GUI built with a toolkit such as Qt/PySide or
  another suitable framework. The same CI pipeline and start scripts will
  launch GUI builds using the `.venv` workflow when the interface stabilizes.
- Explore macOS notarization and automated code signing once an Apple
  Developer
  ID certificate is available and the release process is more formalized.
- Consider adding a self-hosted Apple Silicon runner or leveraging cross-
  compilation to produce native arm64 binaries when regular access to Apple
  Silicon hardware becomes available.
- Expand packaging options (e.g. Windows installers or Linux `.deb` files) to
  streamline distribution without compromising the license constraints.
